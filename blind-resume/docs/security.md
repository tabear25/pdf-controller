# 安全設計

## 守りたいもの

候補者の履歴書・職務経歴書（PDF）に含まれる個人情報です。目標は 2 つあります。

1. PDF の中身が、利用者の PC の外に出ないこと。
2. 書き出した PDF から、黒塗りした範囲の情報も、元の PDF の文字情報・メタデータも復元できないこと。

## 想定する脅威

| 脅威 | 例 | 主な対策 |
|---|---|---|
| 細工された PDF によるスクリプトの実行 | PDF.js の脆弱性（例：CVE-2024-4367）を突き、画面遷移やリンクで中身を持ち出す | 下の「スクリプトを実行させない」 |
| アプリ自身による送信 | 解析やエラー送信の仕組み、CDN からの読み込み | 通信の遮断（CSP）、外部参照の検査、仕組み自体を入れない |
| 黒塗りの下の文字の残存 | 黒い四角を重ねただけで、下に文字が残る | ページを画像にして塗り、元の PDF の構造を引き継がない |
| メタデータ・注釈・添付ファイルの残存 | 文書情報や添付ファイルに氏名が残る | 同上。書き出し後に自動で検査する |
| 端末への残存 | ブラウザの保存領域や履歴に残る | 保存系の API を使わない。タイトルと URL を固定する |
| 配信物のすり替え（公開して使う場合） | ホストのアカウントや main ブランチを握られ、持ち出すコードに差し替えられる | アカウントの守り、ホスト側でビルドしない運用、SHA-256 の公開 |

## スクリプトを実行させない

CSP は通信を止めますが、画面遷移（`location` の書き換えなど）による持ち出しは止められません。そのため、スクリプトを実行させない対策を重ねます。

1. **最新の PDF.js（6.5.438）**：6.x では、PDF の内容から JavaScript を組み立てて実行する経路（以前の `isEvalSupported` で制御していたもの）が取り除かれた。オプション自体もなくなっている。
2. **CSP でスクリプトを限定する**：インラインのスクリプトは、ビルド時に計算した SHA-256 だけを許可する。`'unsafe-inline'` と `'unsafe-eval'` は許可しない。`script-src` には `blob:` も `data:` も入れない。
3. **Trusted Types**：`require-trusted-types-for 'script'` により、innerHTML などの HTML を解釈させる書き込み、文字列からのスクリプト生成（eval、new Function）、文字列の URL からの Worker 生成が、ブラウザの仕組みとして使えなくなる。許可するポリシーは `blind-resume-worker` の 1 つだけで、アプリ自身が作った blob: の URL しか通さない。
4. **解析は Worker の中**：PDF を解析するコードは Worker で動き、画面にも画面遷移にも触れられない。Worker は作成元の CSP を引き継ぐので、Worker の中でも通信や eval は止まる（確認済み）。
5. **HTML を組み立てない**：PDF から取り出した文字は、textContent だけで画面に出す。画面の部品は `createElement` で作り、HTML の文字列は使わない。ビルド後に、innerHTML などが成果物に残っていないかを検査する。
6. **PDF のリンクを作らない**：注釈の層とテキストの層を DOM として作らない。XFA も描かない。

### `'wasm-unsafe-eval'` を許可している理由

PDF.js 6.x は、スキャン PDF でよく使われる CCITT・JBIG2 と、JPEG 2000 の復号を WASM で行います。許可しないと、これらの画像が真っ白になります（事前の確認で、CCITT の画像が描かれないことを確かめた）。PDF.js には JS 版の代替もありますが、URL からの動的な import で読み込む作りのため、1 ファイル・通信遮断の構成では使えません。

`'wasm-unsafe-eval'` が許すのは WASM のコンパイルだけで、JavaScript の eval と new Function は引き続きブロックされます。WASM のコードは、渡された関数しか呼べず、画面や通信には直接触れられません。一方、PDF.js は PDF の中の計算式（PostScript 関数）を WASM に変換して実行するので、その中身は攻撃者が左右できます。これを突いてデータを持ち出すには、ブラウザ本体の脆弱性が必要です。この点は利用者の了承を得ています（[decisions.md](decisions.md)）。

## 通信の遮断

- CSP：`default-src 'none'`、`connect-src 'none'`、`form-action 'none'`、`base-uri 'none'`、`object-src 'none'`、`frame-src 'none'` など。`worker-src` は `blob:` だけ。
- ライブラリ、cMap、フォント、WASM は、すべて `index.html` に埋め込む。実行時に読み込むファイルはない。
- アクセス解析やエラー送信の仕組みは入れない。ログはブラウザのコンソールに出すだけ。
- 公開するときは、同じ CSP をレスポンスヘッダーでも返し、meta タグでは効かない `frame-ancestors 'none'` を足す（`vercel.json`）。ホストが自動で差し込むスクリプトがあっても、ヘッダーの CSP で止まる。

## 何も残さない

- localStorage、sessionStorage、IndexedDB、Cache Storage、Service Worker は使わない（ビルド後に検査する）。
- `document.title` と URL は固定する。ブラウザの履歴に、候補者の名前やファイル名が残らない。
- 別のファイルを開いたときやクリアしたときは、PDF.js の文書を破棄し、Worker を終了し、canvas の画素を解放する。読み込んだバイト列は Worker に移すので、メイン側にはコピーが残らない。
- パスワードは PDF.js に渡したらすぐ入力欄から消し、保存しない。

JavaScript には、メモリを確実に消去する手段がありません。参照を捨てたあと、実際にメモリが回収される時期はブラウザが決めます。

## 検証のしかた

- ビルド時：外部参照、HTML 注入の口、保存系の API がないこと、ライセンス一覧と同梱物の一致（`scripts/postbuild.mjs`、`scripts/build-plugin.mjs`）
- E2E テスト：すべての操作で、アプリ自身のファイル以外への通信が 0 件、CSP の違反が 0 件、想定外のコンソールの警告が 0 件（`tests/e2e/harness.ts`）。file:// と静的サーバーの両方で確かめる。
- M3 以降：書き出した PDF を、アプリとは別の実装（pikepdf、poppler）で調べ、ダミーの氏名などの文字列が残っていないこと、黒塗りの範囲が黒であることを確かめる。

## アプリの外にある前提

次のものは、アプリでは防げません。

- **ブラウザの拡張機能**：拡張機能はページの中身を読める。拡張機能が既定で動かない、シークレット ウィンドウでの利用を勧める。
- **ブラウザ本体の脆弱性**：ブラウザを最新に保つ。
- **配信物のすり替え**：公開して使う場合、GitHub と Vercel のアカウントに 2 段階認証を設定する。main ブランチにはブランチ保護をかける。ホスト側ではビルドせず、コミットした `dist/` をそのまま配る。`dist/index.html.sha256` で、配っているファイルが同じものか確かめられる。
- **書き出した PDF の扱い**：ダウンロードしたファイルの保存先と渡し先は、運用で管理する。
