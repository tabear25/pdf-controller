# 依頼：ブラインドレジュメ作成ツールの開発（ブラウザで完結する PDF 黒塗り Web アプリ）
PRはコントローラーの方のリポジトリで出して

空のディレクトリから新しく作ってほしい。まずは第 7 章の進め方に沿って、計画と質問を返してほしい。

## 1. 背景と目的（共有）

- 採用業務で、候補者の履歴書や職務経歴書（PDF）から、氏名、写真、連絡先など個人を特定できる情報や属性を伏せた PDF（ブラインドレジュメ）を作る必要がある。
- 伏せる対象をルールで指定する方式は、想定外の箇所からの漏れが起きやすい。そこで、利用者が画面上でドラッグして範囲を選び、その範囲を黒塗りする方式にする。
- 利用者は採用担当者で、エンジニアではない。Python などが入っていない社用 PC でも、ブラウザだけで使えるようにしたい。
- 伏せる範囲や渡し先は運用で決めるので、ツールは特定の書式に依存しない汎用の黒塗りツールとして作る。

ゴール状態：利用者が PDF を開き、伏せたい範囲をドラッグで選んで書き出すと、選んだ範囲の情報を復元できない PDF が手に入る。あわせて、その PDF に元の文字情報やメタデータが残っていないことを、ツールが自動で検査して示す。

## 2. 設計の前提（共有）

ここはツールの安全性の根幹にあたる。変える必要があると考えた場合は、実装の前に相談してほしい。

- 処理はすべて利用者のブラウザ内で行う。候補者の個人情報を扱うので、PDF のデータが利用者の PC の外に出ない構成にする。
- 書き出しは、ページを画像にする方式で行う。各ページを画像として描画し、選んだ範囲を黒で塗りつぶした画像から新しい PDF を組み立てる。元の PDF のテキスト層、メタデータ、注釈、添付ファイルを引き継がないので、黒塗りの下に文字が残る事故は構造上起きない。出力 PDF の文字は選択も検索もできなくなるが、これは許容済みである。
- 入力 PDF は、信頼できないデータとして扱う。PDF は候補者やエージェントなど外部から届き、PDF.js にも細工された PDF でスクリプトが実行される脆弱性が過去にあった（例：CVE-2024-4367）。CSP では画面遷移を使った持ち出しまでは防げないので、通信の遮断に加えて、スクリプトを実行させない対策を重ねる（第 4 章）。
- 最終判断は人が行う。ツールが見つけた箇所は候補として示すにとどめ、塗るかどうかは利用者が決める。

## 3. 作ってほしいもの（依頼）

画面の文言は日本語にし、使い方の短い説明を画面に表示する。

### 3-1. 必須

**読み込みと表示**

- PDF をファイル選択かドラッグ＆ドロップで読み込み、全ページを縦に並べて表示する。
- 日本語の PDF を正しく表示する。フォントを埋め込んでいない PDF に備えて、PDF.js の cMap と標準フォントのデータを同梱する。
- スキャン PDF（画像だけの PDF）でも、表示と黒塗りができるようにする。

**範囲の選択**

- ページ上をドラッグして矩形を作る。作った矩形は、選択、移動、サイズ変更、削除（Delete キー）ができるようにする。
- 元に戻す・やり直す（Ctrl+Z、⌘Z など）に対応する。
- 矩形の座標は、画面のピクセルではなく、倍率に依存しない単位で持つ（例：ページの回転を反映した表示向きで、倍率 1 のときのポイント単位）。回転したページや、CropBox の原点がずれたページでも、位置がずれないようにする。
- 選んだ矩形を、全ページの同じ位置に適用できるようにする。サイズや向きが違うページには適用せず、その旨を表示する。
- 編集中の矩形は半透明で表示し、下の文字を見ながら位置を合わせられるようにする。

**同じ文字列の候補表示**

- 矩形を作ったら、範囲内の文字を読み取り、検索語の候補として示す。利用者が検索語を編集してから、文書全体を検索できるようにする。
- 検索語を直接入力して探す欄も設ける（ふりがな、ローマ字表記、出身校名などを想定）。
- 検索では、全角と半角の違い（NFKC 正規化）と空白の有無を区別しない。均等割り付けで 1 文字ずつ離れた氏名（例：「山 田 太 郎」）も一致させる。正規化で文字数が変わる場合も、元の位置に正しく対応付ける。
- 一致した箇所は「未確認」の候補として表示し、1 件ずつ、またはまとめて「塗る」「塗らない」を選べるようにする。すでに塗る範囲に含まれている箇所は、候補から除く。
- 文字単位の位置は近似になるので、候補の矩形は文字を確実に覆うよう、少し大きめにとる。
- 文字情報のない PDF では、この機能が使えないことを画面に表示する。

**書き出し**

- 各ページを指定の解像度（既定は 200dpi。150、200、300 から選ぶ）で描画し、矩形の範囲を不透明な黒で塗りつぶす。塗る範囲はピクセルの境界まで外側に広げ、縁に文字の一部が残らないようにする。
- 塗りつぶした画像だけで新しい PDF を組み立てる。ページの大きさは元のページの表示サイズに合わせ、回転したページは正しい向きで出力する。
- 文書情報（タイトル、作成者など）は空にし、元の PDF からは何も引き継がない。
- ファイル名の既定値は、元のファイル名を使わない中立な名前（例：blind_resume_20261106_1530.pdf）にし、利用者が編集できるようにする。元のファイル名には、候補者の氏名が入っていることが多いからである。
- 「未確認」の候補が残っている場合は、書き出しの前に一覧を示して判断を求める。
- 画面の表示と書き出しで描画の設定（intent や annotationMode など）を揃え、画面で見えていないものが書き出しに出ないようにする。
- ページが大きくブラウザの描画の上限を超えそうな場合は、解像度を自動で下げ、その旨を表示する。

**書き出し後の自動検査と確認画面**

- 生成した PDF を読み込み直し、次の点を自動で検査する。
  - 全ページで、テキストが 0 件になっている。
  - 注釈、添付ファイル、しおり、スクリプトが含まれていない。
  - 文書情報に、元の PDF 由来の値が入っていない。
  - ページ数が想定と一致している。
  - 各矩形の範囲のピクセルが黒になっている（縁から 1〜2px 内側で判定する）。
- 検査の結果を画面に示し、すべて合格したときだけダウンロードできるようにする。
- 生成した PDF そのものを描画したプレビューを、元の PDF と並べて表示する。
- 確認画面に、漏れやすい箇所のチェックリストを表示する（氏名とふりがな・ローマ字表記、写真、性別欄、生年月日・年齢、住所・最寄り駅、電話・メール・URL、ヘッダーとフッター、自己 PR や志望動機の中の固有名詞、署名・印影）。項目はコード上の 1 か所にまとめ、運用に合わせて変えやすくする。

### 3-2. できれば入れる

- 正規表現による候補の自動検出を入れる。対象はメールアドレス、電話番号（全角数字や各種のハイフンを含む）、郵便番号、URL、年齢の表記（「満 25 歳」など）とし、結果は「未確認」の候補として表示する。日付や年号は候補が多くなりすぎるので、既定では検出せず、利用者が有効にできるようにする。
- 拡大、縮小、幅に合わせる表示を入れる。
- ページ単位で出力から外せるようにする（エージェントの推薦文の表紙などを想定）。
- パスワード付きの PDF を、その場でパスワードを入力して開けるようにする（パスワードは保持しない）。
- 書き出しの進み具合と、出力ファイルのサイズを表示する。

### 3-3. 今回は扱わない（次の段階で検討する）

- 位置のテンプレート保存と、複数ファイルの一括処理は、処理件数が分かってから検討する。
- 出力 PDF への文字情報の付与は、必要になった時点で、黒塗り後の画像から OCR で付け直す方式で検討する。元の PDF の文字は使わない。
- サーバーでの処理、ログイン、すべてを自動で塗る機能は、今回の範囲に含めない。

## 4. 安全性の要件（依頼）

- Content-Security-Policy を meta タグで設定し、外部への通信を遮断する（connect-src 'none'、form-action 'none' など）。インラインのスクリプトは、可能ならハッシュで許可する。Worker や同梱データの読み込みに要るローカルの参照（blob: や data:）だけを、必要な範囲で許可する。
- ライブラリ、cMap、フォント、WASM などはすべて成果物に同梱し、実行時に CDN から読み込む箇所がない状態にする。
- ログやエラーはブラウザのコンソールに出すだけにし、アクセス解析やエラー送信の仕組みは入れない。
- PDF.js は最新の安定版を使い、isEvalSupported を false にする。CSP でも 'unsafe-eval' は許可しない。WASM のために 'wasm-unsafe-eval' が必要な場合は、理由とともに報告する。
- PDF から取り出した文字列は、textContent などを使って文字として画面に出す。HTML として解釈させる経路は作らない。
- PDF の中身や取り出した文字は、メモリの中だけで扱う。localStorage、IndexedDB、Cache Storage、Service Worker は使わず、ページを閉じれば何も残らない状態にする。
- 別のファイルを開いたときや、クリアの操作をしたときは、前のファイルのデータを解放する。
- リポジトリに入れる PDF は、テスト用のダミーに限る。.gitignore で、テスト用の置き場以外の PDF を除外する。

## 5. 技術構成（依頼）

次を推奨とする。より良い選択肢があれば変えてよいが、変えた点と理由を報告してほしい。

- Vite と TypeScript で作る。UI フレームワークは使っても使わなくてもよい。
- 表示と文字情報の取得には、pdfjs-dist（Apache-2.0）を使う。
- PDF の組み立てには、pdf-lib か jsPDF（いずれも MIT）を使う。
- 成果物は、すべてを 1 ファイルにまとめた自己完結の index.html にする（例：vite-plugin-singlefile）。この 1 ファイルを、ダブルクリックで開く使い方（file://）と、静的ホスティングでの公開の両方で使えるようにする。file:// ではモジュールや Worker の読み込みに制約があるので、実際に file:// で開いて動作を確かめる。
- ライブラリは、MIT、Apache-2.0、BSD などの許容的なライセンスのものから選ぶ。AGPL の MuPDF.js などは対象外とする。第三者ライセンスの一覧を成果物に含め、1 ファイルで配布しても一覧が付いてくるよう、アプリの画面からも見られるようにする。
- 対象ブラウザは、Windows と Mac の最新版の Chrome と Edge を想定する（第 9 章で確認する）。

## 6. 検証とテスト（依頼）

**テスト用のダミー PDF**

実在の人物の情報は使わず、スクリプトで生成する。開発環境では Python や Node.js を使ってよい（利用者の PC には不要）。次の条件を満たすダミー PDF を、それぞれ用意する。

1. フォントを埋め込んだテキストで、A4 の 2 ページ以上ある。全ページのヘッダーに氏名があり、自己 PR の中に氏名とふりがな、写真枠にダミー画像、メール、電話番号、URL、郵便番号、生年月日が入っている。
2. 日本語フォントを埋め込んでいない。
3. 均等割り付けで 1 文字ずつ離れた氏名を含む。
4. 回転したページ（/Rotate 90 と 270）、横向きのページ、サイズ違い（B5、A3）のページが混ざっている。
5. CropBox が MediaBox と異なるページを含む。
6. 文書情報、注釈（コメント）、フォームの入力値、添付ファイルに、ダミーの氏名が入っている。
7. 画像だけのスキャン PDF である。
8. スキャン画像に、透明なテキスト層が付いている。

**自動テスト**

- 単体テストで、座標の変換（回転 0、90、180、270 と CropBox のずれ）、正規化と元の位置の対応付け、検索を確かめる。
- Playwright による E2E テストで、読み込み、ドラッグでの矩形作成、書き出し、自動検査までの流れを、上のダミー PDF すべてで通す。
- 出力 PDF の全オブジェクトを走査し、ダミーの氏名などの文字列がどこにも含まれないことを確かめる。
- 出力 PDF を描画し直し、黒塗りした範囲のピクセルが黒であることを確かめる。
- 操作の最初から最後まで、アプリ自身のファイル以外への通信が 0 件であることを確かめる。
- ビルドした index.html を、file:// で開いた場合と、ローカルの静的サーバーで開いた場合の両方でテストする。
- テストを実行できない環境の場合は、その理由と、代わりに行った確認を報告する。

## 7. 進め方（依頼）

1. この依頼文を docs/requirements.md として保存し、以後の判断の基準にする。
2. 実装の前に、計画（マイルストーンの分け方、構成、主なリスク）と質問をまとめて提示する。回答を受けてから実装に入る。
3. 次の順に進める。各マイルストーンの終わりに、できたこと、テストの結果、残っている課題を短く報告し、画面のスクリーンショットを docs/screenshots に保存する。
   - M1：雛形を作り、PDF の読み込みと表示（日本語の cMap を含む）、CSP、1 ファイルのビルドを整える。file:// で動くことも確かめる。
   - M2：矩形の作成と編集、座標の扱い、全ページへの適用を作る。
   - M3：書き出し、自動検査、確認画面を作る。
   - M4：同じ文字列の候補表示、検索欄、未確認の候補の扱いを作る。
   - M5：3-2 の項目を入れる。
4. 目的、範囲、第 2 章の前提を変える必要が出たら、実装を止めて相談する。範囲内で小さく戻せる改善は、確認なしで進めてよい（報告には含める）。
5. コードにはインラインコメントを書かず、設計の判断や注意点は README と docs/ にまとめる。

## 8. 完了条件と成果物（依頼）

成果物は、ソースコード一式とテスト、ビルド済みの dist/index.html（1 ファイルで完結するもの）、README.md、第三者ライセンスの一覧とする。README には、利用者向けの使い方、安全設計の説明、既知の限界、ビルドとテストの方法、公開の手順を書く。

完了条件は次のとおりとする。

- 第 6 章の自動テストが、すべて通っている。
- 書き出した PDF に、テキスト、注釈、添付ファイル、元の文書情報が残っていない。
- 日本語の PDF が、フォントの埋め込みの有無にかかわらず正しく表示される。
- 操作中の外部への通信が 0 件である。
- dist/index.html が、file:// でも静的ホスティングでも動く。

最後に、作ったもの、使い方、テスト結果、既知の限界、この依頼から変えた点とその理由、未解決の論点を報告してほしい。

## 9. 着手前に確認してほしいこと（確認）

計画を示すときに、次の点もあわせて質問してほしい。ほかに判断が必要な点があれば、それも挙げてほしい。

1. 公開先はどこにするか（Cloudflare Pages、GitHub Pages、社内のサーバーなど）。社内限定のアクセス制限を付けるか。公開の作業は、この回答を受けてから行う：Vercel or Renderだとうれぴい
2. 月に何件くらい処理するか。入力の PDF は主にどこから届くか（HRMOS からの出力、エージェント経由、スキャンなど）：ローカルファイルのアップロード
3. 社用 PC の OS とブラウザは何か：windows
