# 実装計画と確認事項

[requirements.md](requirements.md)（依頼文）を基準にした、実装前の計画、主なリスク、質問です。回答を受けたら、確定した事項を `decisions.md` に記録してから M1 に入ります。

## 1. 結論

1. 構成は依頼の推奨どおり（Vite + TypeScript、pdfjs-dist、pdf-lib、1 ファイル化）で進められます。土台になる部分は、捨てコードで事前に確かめました（第 3 節）。
2. ただし PDF.js 6.x で事情が変わっていて、依頼から 2 点を変える必要があります。
   - `isEvalSupported` は 6.x で廃止されていて、設定できません。eval を使うコード自体がなくなりました。代わりに、CSP（'unsafe-eval' なし）と Trusted Types で eval の類を止め、そのことをテストで確かめます。
   - スキャン PDF の表示に `'wasm-unsafe-eval'` が要ります。許可しないと、スキャンでよく使われる白黒画像の圧縮（CCITT、JBIG2）と JPEG 2000 の画像が真っ白になります（質問 1）。
3. file:// で開いた場合、PDF.js の Worker はそのままでは起動しません（Chromium の制約です）。ビルド時に classic 形式へ変換すれば動くことを確認しました。
4. 公開先は Vercel（Hobby、個人アカウント）にします。使うのは本人だけで、PDF がサーバーに届かない構成なので、アクセス制限は付けません。公開して使う場合の安全性は、「配信物を誰が書き換えられるか」、つまり GitHub と Vercel のアカウントの守りに左右されます（質問 2、回答済み）。
5. 私の環境では Linux の Chromium でしか試せません。Windows の Edge と Chrome での確認は、GitHub Actions での自動テストと、社用 PC での 1 回の確認で補いたいと考えています（質問 3）。

## 2. 置き場所と進め方

- pdf-controller リポジトリに `blind-resume/` を新設し、その中に一から作ります。ルート直下の既存の Tkinter アプリには触れません。
- 例外として、リポジトリのルートに `.gitignore` を足し、テスト用の置き場以外の PDF を除外します。既存アプリは入力 PDF の隣に出力を書くので、リポジトリ内で使うと候補者の PDF がコミットされるおそれがあります。このリポジトリは公開なので、コミットされると誰でも見られる状態になります。
- pdf_black_out リポジトリ（README だけ）は使いません。
- ブランチ `ccr-3db2bf48-fjpogy` の draft PR に M1〜M5 を積み、完了したら Ready for review にします。
- 各マイルストーンの終わりに、できたこと・テストの結果・残りの課題を報告し、画面を `docs/screenshots/` に保存します。

## 3. 事前検証（捨てコードでの確認）

依頼どおりの CSP（スクリプトはハッシュでのみ許可、`connect-src 'none'` など）と Trusted Types を meta タグで設定した 1 ファイルの HTML を作り、確かめました。HTML には PDF.js の本体、Worker、cMap、標準フォント、WASM をすべて埋め込み、file:// と http の両方で開いています。

確認した環境は、pdfjs-dist 6.5.438（2026-11-01 公開の最新安定版）と Chromium 153.0.8010.12（Playwright 1.63.0）です。OS は Linux です。

| 確かめたこと | 結果 |
|---|---|
| `isEvalSupported` | 6.5.438 では、`getDocument` の型定義にも実装にも、このオプションがない。ビルド済みのコード（pdf.mjs、pdf.worker.mjs）には `eval(` も `new Function(` もない |
| eval、new Function、外部への fetch、innerHTML、文字列の URL からの Worker 生成 | すべてブロックされた（file://、http とも） |
| blob: から作った Worker にかかる CSP | 作成元の CSP をそのまま引き継いだ。Worker の中でも fetch、eval、data: の import がブロックされた。WASM は `'wasm-unsafe-eval'` があるときだけ動いた |
| フォントを埋め込んでいない日本語（HeiseiKakuGo-W5、UniJIS-UCS2-H） | 同梱の cMap を、通信なしで Worker に渡せた。文字の取得と描画もできた |
| CCITT G4 のスキャン画像 | `'wasm-unsafe-eval'` があれば描画された。ないと真っ白だった（黒い画素が 0）。PDF.js には JS 版の代替もあるが、URL からの動的 import で読み込む作りなので、1 ファイルで通信を遮断した構成では使えない |
| file:// で、blob: から module 形式の Worker を起動 | 起動しない（CSP がなくても同じ）。classic 形式なら起動する。PDF.js の Worker の `export` 1 か所と `import.meta.url` 2 か所を置き換えて classic で起動したところ、上の全項目が file:// でも通った |
| 残っている課題 | 埋め込みのない欧文の標準フォントについて、PDF.js が代わりのフォントの指定に `url()` を混ぜるため、font-src の違反が 1 件出る（実害はない）。M1 で解消する |
| API の変化 | 6.x の `PDFDocumentProxy` には `destroy()` がなく、文書の破棄は `loadingTask.destroy()` で行う |

## 4. 構成

### 4-1. 技術

| 用途 | 採用するもの | 補足 |
|---|---|---|
| ビルド | Vite 8、vite-plugin-singlefile | 1 ファイルの `dist/index.html` を作る。後処理で CSP のハッシュを計算して埋め込む |

| UI | フレームワークは使わない | 依存と、HTML を扱う経路を減らすため。画面の規模は、素の DOM 操作で足りる |

| PDF の組み立て | pdf-lib 1.17.1 | 2021-11 以降は更新がない。ただし使い方を「自分で作った画像を並べる」だけに絞り、出力は検査で確かめるので採用する。jsPDF は、作成ソフト名などを既定で書き込むため選ばない |
| 単体テスト | Vitest | |
| E2E テスト | Playwright（@playwright/test 1.63.0） | 手元の Chromium の版に合わせる |
| ダミー PDF の生成と出力の検査 | Python（reportlab、pypdf、pikepdf、Pillow、img2pdf）、poppler（pdftoppm） | 出力の検査は、アプリとは別の実装（qpdf 系のライブラリと poppler）で行う |

### 4-3. データの流れ

1. ファイル選択かドラッグ＆ドロップで受け取り、メモリの中だけで扱う。
2. PDF.js が Worker の中で解析する。画面には canvas で描画し、文字は `getTextContent` でメモリに取る。
3. 矩形は、ページごとに「表示の向きで、倍率 1 のときのポイント」で持つ。PDF.js の `viewport(scale 1)` と同じ座標系なので、回転と CropBox のずれは PDF.js 側の変換にまとめて任せられる。
4. 書き出しでは、同じ描画設定のまま、指定の解像度で描画し直す。矩形を外側の画素の境界まで広げて黒で塗り、JPEG にしてから、pdf-lib で 1 ページ 1 画像の PDF に組み立てる。
5. 出力を読み直して検査し、元の PDF と並べてプレビューする。検査にすべて合格し、確認のチェックが入ったときだけダウンロードできる。
6. 別のファイルを開いたときやクリアしたときは、PDF.js の文書を破棄し、Worker を終了して作り直す。canvas、文字、候補、操作の履歴も捨てる。

描画設定は画面と書き出しで共通にし、コード上の 1 か所で定義します。

- intent は `'display'` にする。
- annotationMode は `ENABLE` にする。注釈とフォームの見た目は、画面にも書き出しにも描く。フォームに入力済みの履歴書の中身を落とさないためで、見え方は印刷と同じになる。コメントの本文のように、画面に描かれないものは書き出しにも出ない。
- XFA とスクリプトは無効にする。注釈とテキストの層は、DOM として作らない。

## 5. 安全設計

対策を何層にも重ねます。

1. 入力 PDF を解析するコードは、Worker の中で動かす。Worker は画面にも、画面遷移にも触れない。
2. CSP は次のとおりにする（ハッシュはビルド時に計算する）。

   ```
   default-src 'none';
   script-src 'sha256-…' 'wasm-unsafe-eval';   ← 'wasm-unsafe-eval' は質問 1 の回答による
   style-src 'sha256-…';
   worker-src blob:;
   connect-src 'none';
   img-src 'none';  font-src 'none';             ← M1 で PDF.js に要るかを確かめ、要るなら blob: だけを足す
   form-action 'none'; base-uri 'none'; object-src 'none'; frame-src 'none';
   manifest-src 'none'; media-src 'none';
   require-trusted-types-for 'script'; trusted-types blind-resume-worker
   ```

   `blob:` は `worker-src` にだけ入れ、`script-src` には `blob:` も `data:` も入れません。入れると、Worker の中でスクリプトを組み立てて実行できてしまうためです。

3. Trusted Types を使う。innerHTML のように HTML を解釈させる書き込み、文字列からのスクリプトの生成、文字列の URL からの Worker の生成が、ブラウザの仕組みとして使えなくなる。Worker は、アプリ自身が作った blob: の URL だけを通す。PDF.js の本体（pdf.mjs）が innerHTML などを使っていないことは確認済み。
4. PDF から取り出した文字列は、textContent だけで画面に出す。HTML を組み立てる関数は持たない。ビルドの後で、innerHTML などが成果物に残っていないかを検査する。
5. 画面遷移による持ち出しは、CSP では防げない。そのため、1〜4 でスクリプトを実行させないことに加えて、PDF の中のリンクを画面に作らない（注釈の層を作らない）。
6. 何も残さない。保存のための API（localStorage など）は使わない。`document.title` と URL は固定し、ブラウザの履歴に候補者の名前などが残らないようにする。ログはコンソールに出すだけにする。
7. 公開するときは、HTTP ヘッダーでも同じ CSP を返す。meta タグでは効かない指示（`frame-ancestors 'none'` など）は、ヘッダーで補う。
8. 配信物を固定する。ホスト側ではビルドせず、コミットした `dist/` をそのまま配る。README に `index.html` の SHA-256 を載せる。main にはブランチ保護をかけ、関係するアカウントには 2 段階認証を設定する。

## 6. マイルストーン

### M1：土台（読み込み、表示、CSP、1 ファイル、file://）

作るもの

- `blind-resume/` の雛形と、画面の骨組みを作る。文言は日本語にし、使い方の短い説明と「このファイルは外部に送信されません」の表示を置く。このツールは何も送らないので、ボタンは「アップロード」ではなく「開く」と書く。
- PDF をファイル選択かドラッグ＆ドロップで読み込み、全ページを縦に並べて表示する。描画は、見えている付近のページから順に行う。
- PDF.js の設定を 1 か所に集める。Worker の classic 化、cMap・標準フォント・WASM の同梱と供給、描画設定の定数がここに入る。
- 別のファイルを開いたときやクリアしたときに、前のファイルのデータを解放する。
- ビルドの後処理を作る。CSP のハッシュの計算と埋め込み、外部への参照や HTML 注入の口が残っていないかの検査、第三者ライセンス一覧の生成（画面からも見られるようにする）、`index.html` の SHA-256 の出力を行う。
- ルートの `.gitignore` と、ダミー PDF の生成スクリプトを作る。ダミーは第 6 章の 8 種に、パスワード付きのものと、JPEG 2000 の画像を含むものを足す。
- 質問 3 で了承をもらえたら、GitHub Actions の CI を作る（Linux、Windows の Edge と Chrome、macOS）。

テスト：全ダミーを file:// と静的サーバーの両方で開き、次を確かめる。

- 全ページが描画される。
- 日本語の文字が取得できる。
- エラー、CSP の違反、外部への通信が、どれも 0 件である。

完了の目安：`dist/index.html` をダブルクリックで開き、すべてのダミーが表示できる。

作るもの

テスト

- 単体テストで、座標の変換を確かめる。回転 0・90・180・270 と CropBox のずれの組み合わせを、PDF.js の viewport の結果と突き合わせる。操作の履歴も確かめる。
- E2E テストで、回転・CropBox・サイズ違いのダミーを使い、矩形の作成と全ページへの適用を確かめる。

### M3：書き出し、自動検査、確認画面

作るもの

- 書き出し
  - 150・200・300dpi（既定は 200）で描画し、矩形を外側の画素の境界まで広げて黒で塗る。
  - JPEG にして、pdf-lib で組み立てる。文書情報は書かず、ページの大きさは表示サイズに合わせ、回転も反映する。
  - ブラウザの描画の上限を超えそうなページは、解像度を下げ、その旨を表示する。
  - ファイル名の既定値は中立な名前にし、利用者が編集できるようにする。
  - 未確認の候補が残っていれば、書き出しの前に一覧を示す（候補そのものは M4 で作り、ここにつなぐ）。
- 自動検査
  - 依頼の項目を検査する。テキストが 0 件、注釈・添付ファイル・しおり・スクリプトがない、文書情報、ページ数、矩形の範囲が黒（縁から 2px 内側で、しきい値つきで判定）。
  - あわせて、出力の構造を許可リストで検査する。想定外の種類のオブジェクトが 1 つでもあれば不合格にする。
- 確認画面：元の PDF と出力を並べたプレビュー、検査の結果、チェックリスト、確認のチェックを置く。検査に合格し、確認のチェックが入ったときだけダウンロードできる。

テスト

- E2E テストで、全ダミーについて「開く → 塗る → 書き出す → 検査 → ダウンロード」を通す。
- 出力を pikepdf で全オブジェクト走査し、ダミーの氏名などがどこにもないことを確かめる。圧縮されたストリームの中、UTF-16、16 進の文字列も対象にする。
- 出力を poppler で描画し直し、黒であることを独立に確かめる。
- 外部への通信が 0 件であることを確かめる。

### M4：同じ文字列の候補表示、検索欄、未確認の候補の扱い

作るもの

- 矩形の範囲内の文字を読み取り、検索語の候補として示す。利用者が編集してから、文書全体を検索できる。
- 検索語を直接入力する欄を設ける。
- 検索では、NFKC 正規化と空白の有無に加えて、英字の大小、ひらがなとカタカナ、ハイフン類の違いも区別しない。正規化で文字数が変わっても、元の位置に対応付ける。
- 均等割り付けの氏名も一致させる。文字が別々の断片に分かれていても一致する。
- 候補の矩形は、文字を確実に覆うよう少し大きめにとる。
- 候補は「未確認」「塗る」「塗らない」を、1 件ずつでもまとめてでも選べる。すでに塗る範囲に含まれている候補は除く。
- 文字情報のない PDF では、この機能が使えないことを表示する。

テスト

- 単体テストで、正規化で文字数が変わる例（ｶﾞ→ガ、㈱→(株)、①→1、ﬁ→fi、㍻→平成）、空白と均等割り付け、断片をまたぐ一致、候補の矩形が文字を覆うことを確かめる。
- E2E テストで、ヘッダーの氏名、自己 PR の中の氏名とふりがな、均等割り付け、透明なテキスト層、フォントを埋め込んでいない PDF を確かめる。

## 7. 主なリスク（影響の大きい順）

1. **塗る位置が、利用者が画面で見た位置からずれる（回転、CropBox、倍率）。** 漏れに直結します。依頼の自動検査（矩形の範囲が黒か）は、書き出しと同じ座標変換で範囲を求めるので、変換そのものの誤りは見つけられません。対策は 3 つです。
   - 座標の基準を 1 つに決め、表示・候補・書き出し・検査のすべてで共有する。
   - 単体テストで、変換を PDF.js の viewport と突き合わせる。
   - E2E テストでは、生成スクリプトが記録した氏名の位置を Python 側で独立に変換し、poppler で描画した出力と照合する。確認画面の並列プレビューも、この誤りを人が見つける最後の機会になる。
2. **自動検査の合格が「伏せるべきところを全部伏せた」と受け取られる。** 検査が確かめるのは書き出しの仕組みであって、塗り漏れではありません。写真の中の文字や、スキャン PDF の氏名は、検索でも見つかりません。対策として、確認画面の文言でこのことを明示し、チェックリストと確認のチェックを置きます。
3. **配信経路の乗っ取り（公開して使う場合）。** 第 5 節の 8 と質問 2 で扱います。
4. **社用 PC の環境の違い。** 拡張機能、社内のポリシー、Edge の IE モードなどです。拡張機能はページの中身を読めるので、CSP では防げません。対策として、README で InPrivate ウィンドウでの利用を勧めます（拡張機能が既定で無効になり、履歴も残りません）。あわせて実機で確認します（質問 3）。

6. **文字の位置が近似なので、候補の矩形が足りないことがある。** 余白を大きめにとり、人が確認します。
7. **大きなページや高い解像度で、メモリが足りなくなる。** 上限を超えるときは解像度を下げ、その旨を表示します。A3・300dpi で試します。

## 9. 質問

### 回答が必要なもの

**質問 1. `'wasm-unsafe-eval'` を許可してよいか（M1 の CSP に関わる）**

- 推奨：許可する。
- 決め手：PDF.js 6.x では、スキャン PDF でよく使われる白黒画像の圧縮（CCITT、JBIG2）と JPEG 2000 の復号が、WASM を前提にしています。許可しないと、その画像が真っ白になります（第 3 節で確認済み）。許可されるのは WASM のコンパイルだけで、JavaScript の eval と new Function は引き続きブロックされます。WASM のコードは渡された関数しか呼べず、画面や通信には直接触れられません。
- 最も強い反論：WASM のコンパイルは、ブラウザの中の攻撃面になります。PDF.js は、PDF の中の計算式（PostScript 関数）を WASM に変換して実行するので、その中身は攻撃者が左右できます。ただ、これを突いてデータを持ち出すにはブラウザ本体の脆弱性が要り、CSP が守る範囲の外の話になります。
- 許可しない場合：PDF.js の JS 版の復号部を、ビルド時に取り込むように書き換えます。`'wasm-unsafe-eval'` なしで動きますが、成果物が約 0.5MB 増え、復号は遅くなる見込みです。PDF.js を更新するたびに、書き換えが効いているかの確認も要ります。社の規程で「eval と名の付く指定は一切不可」と決まっている場合は、こちらを選びます。

**質問 2. 公開先とアクセス制限（回答済み、2026-11-06）**

- 回答：会社のチームで使うのではない。個人で使うツールに、仕事用の PC からアクセスしたい。
- 判断：Vercel の Hobby（無料）で進める。
  - Hobby は「非商用の個人利用」に限られます。商用の定義は「関わった人の金銭的な利益を目的とするデプロイ」と広く、仕事に使う道具がこれに当たるかは、文面だけでは決まりません（グレー）。ただ、支払いの受け付け、広告、販売といった、商用の典型には当たりません。判断に迷う場合は Vercel のサポートに問い合わせるよう、公式に案内があります。
  - 仮に商用と判断されても、起きるのは有料プランへの移行の求めか、公開の停止です。Vercel に PDF は届かず、何も保存しないので、データが危険にさらされることはありません。file:// で開く使い方も、そのまま続けられます。最悪の場合の影響が小さいので、Hobby で始めてよいと判断しました。
  - 第 1 版の計画では「会社の採用業務は商用にあたる可能性が高い」と書きました。チームで使う前提での見立てで、言い過ぎでした。
- アクセス制限：付けない。配る HTML に秘密はなく、PDF もサーバーに届かないためです。
- 安全性の起点：配信物を書き換えられるのは、GitHub の main に push できる人と、Vercel のアカウントを持つ人です（今はどちらも本人だけ）。両方に 2 段階認証を設定してもらいます。あわせて、ホスト側ではビルドせず、コミットした `dist/` をそのまま配ります（第 5 節の 8）。
- 実機での確認：Vercel は push のたびにプレビューの URL を作ります。そのため、各マイルストーンの成果を、仕事用の PC でそのまま開いて確かめられます（質問 3 の実機確認を兼ねます）。社内のネットワークで vercel.app が止められている場合は、`dist/index.html` をダウンロードし、file:// で使います。
- 念のため：候補者の個人情報を個人のツールで扱うことについて、社内のルールに定めがないかを確認しておくと安全です。説明の要点は「PDF は PC の外に出ない。Vercel が配るのは HTML だけ」の 1 点で足ります。

**質問 3. 社用 PC のブラウザと、実機での確認**

- 社用 PC で使うのは、Edge と Chrome のどちらですか（両方ですか）。
- 推奨：GitHub Actions に、Windows（Edge、Chrome）と macOS で E2E テストを回すジョブを足します。公開リポジトリなので無料です。私の環境は Linux の Chromium だけなので、Windows での file:// のパスや Edge の挙動は確かめられません。
- そのうえで、M1 の終わりに一度、社用 PC で `dist/index.html` をダブルクリックし、ダミー PDF が開けるかを見てほしいです（5 分ほど）。社内のポリシー（拡張機能、ダウンロードの制限、file:// の扱い、Edge の IE モード）は、CI では再現できないためです。
